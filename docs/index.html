claude-science-cockpit

Three verbs, and a record somebody else can check.

A command-line tool for doing work in a kton federation and leaving evidence of it. You name what went in, what came out, and the command you ran. It signs, commits, pushes, pins the permalinks, and answers questions about the graph afterwards — re-verifying every record against keys you configured, never trusting one because it turned up in the registry.

cockpit publish record a result cockpit say bind a claim cockpit ask query the graph

A tour, end to end

Every command below was run against a participant repository built from nothing, and every answer is what came back. Nothing here is illustrative.

Is this repository set up, and bound to what it says?

The first thing anyone runs. It reads the configuration, checks the origin remote matches what the config claims, and names the kernel compiled into the binary. The working directory is shortened here for width.

Record a result.

Three things in — the command, what it read, what it wrote — and everything else out: the foton's id, the hash of every output, the commit that holds them, and a permalink pinned to that commit. The caller did not commit, push, build a permalink, choose a key or sign. Those are the things it cannot get subtly wrong, because it never touches them.

Ask what produced a result.

By the hash of the bytes, not by a filename. verified: true and tier: self are the answer's own work: every record was re-verified against this repository's configured keys before being included, and never trusted from the keyid it declares about itself.

Get an argument wrong.

output where the verb takes outputs. Over MCP a tool schema catches that; at a shell nothing else would, and the record would have been published naming no outputs at all — signed, valid, and wrong. Exit 1 means the call itself was wrong.

$cockpit publish '{"cmd":"mean data/sensor.csv > work/summary.csv","inputs":["data/sensor.csv"],"output":["work/summary.csv"]}'
cockpit: the argument is not valid JSON for this verb: json: unknown field "output"
exit 1

Point it at the wrong repository.

The guard this project exists for. A live demo once had six registries under one parent directory and a session cooperated against the wrong one. Nothing failed — the records were signed, valid, and in the wrong project. Exit 2 means the cockpit understood, and declined.

$cockpit publish '{"cmd":"mean data/sensor.csv > work/summary.csv","inputs":["data/sensor.csv"],"outputs":["work/summary.csv"]}'
cockpit: refusing to act — repo/remote mismatch: cockpit.config.json says someone-else/cockpit-tour, but this repo's origin is cockpit-examples/cockpit-tour — refusing to act against the wrong repo
exit 2

Twelve examples, one property each

Each builds a complete participant repository from nothing, exercises one property, and prints what it saw. The lines under each card are its real assertions. A check that only looked for the absence of an error would pass when a query returned nothing, which is how a suite reports success having verified nothing — so these count what they found.

01

publish

One call records a signed foton — and the point is everything the caller did not do.

no prerequisites
$cockpit publish '{ "cmd": "sum data/in.csv > work/sum.csv", "inputs": ["data/in.csv"], "outputs": ["work/sum.csv"] }'
$cockpit ask '{"query": "producer", "ref": "$HASH"}'
  • ▪ok: the output is committed
  • ▪ok: everything was pushed
  • ▪ok: the reported sha IS the repo's final state
  • ▪ok: and the returned permalink pins it
  • ▪ok: the foton's locator carries a real commit sha
  • ▪ok: which is NOT the one publish returned
  • ▪ok: and it is that sha's parent
  • ▪ok: both name the same file
  • ▪ok: producer found the foton and it verified into a configured tier
  • ▪ok: it is the foton publish reported

claim-ceiling

What may be said, and what may not be decided. A claim comes from a fixed set of templates, and for reproduces the level is measured rather than stated.

$cockpit say '{"subject":"$FOTON","template":"working-on","fields":{"step":"analysis","by-session":"session-1"}}'
$cockpit ask '{"query":"about","ref":"$FOTON"}'

  • ▪ok: and reading it back gives what it SAYS, not just that it exists
  • ▫refused, as it must be: a claim shape this repo does not allow
  • ▪ok: identical bytes were assessed as L0
  • ▫refused, as it must be: a reproduction claim over bytes that do not match
  • ▪ok: still exactly the two claims that were legitimately made
05

trust-tiers

Verified, not declared. A stranger's record goes into the same registry and is still excluded — then the key is configured into a tier and the same record is included. The record did not change. The configuration did.

no prerequisites
$cockpit publish '{"cmd":"produce work/ours.csv","inputs":[],"outputs":["work/ours.csv"]}'
$cockpit ask '{"query":"producer","ref":"$OURS"}'
$cockpit ask '{"query":"producer","ref":"$THEIRS"}'
  • ▪ok: our record is included
  • ▪ok: the stranger's record is NOT included
  • ▪ok: but it IS reported as found and excluded
  • –ok: and the record itself is not in the answer's included set
  • ▪ok: though the answer does account for having found it
  • ▪ok: the same record is now included
  • ▪ok: asking only for tier 'self' excludes the federation record
06

reproduce

Reproducing does not add a record. It adds a signature to the one that is already there.

no prerequisites
$cockpit publish '{"cmd":"sum data/in.csv > work/out.csv","inputs":["data/in.csv"],"outputs":["work/out.csv"]}'
$cockpit ask '{"query":"reproductions","ref":"$HASH"}'
  • ▪ok: the same work is the SAME foton, not a second one
  • ▪ok: and the registry did not grow
  • ▪ok: different bytes are a different foton
  • ▪ok: and that one IS a new record
  • ▪ok: counted by verified signature, not by self-declared keyid

Run the examples

Each builds its own participant repository — a real git repo with a real github.com origin, so the wrong-folder guard runs unmodified. Only the remote's push url points at a local bare repo, so everything completes offline.

Two exit codes

2 means the cockpit understood and refused. 1 means the call itself was wrong. A script needs to tell those apart, so they differ.

Unknown fields are refused rather than ignored, because at a shell nothing else catches a typo in an argument name.

An agent can call them too

The same three verbs are an MCP tool surface, as cockpit_publish, cockpit_say and cockpit_ask. That is a second transport onto the same three handlers, not a second tool — a guard belongs to the configuration, never to how the call arrived.
